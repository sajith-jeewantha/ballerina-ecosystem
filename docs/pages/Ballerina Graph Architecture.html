How the Ballerina knowledge graph works

A map of everything a model should know about Ballerina, stored as small YAML files, checked by a Python package, and turned into a viewer, a JSON export and the checklist that drives training-data generation.

AWhat it is

You want a model that writes good Ballerina code. To train it with supervised fine-tuning (SFT), you need thousands of examples, and they have to cover the whole language and ecosystem. This project is the coverage map for that dataset.

  • Each node is one subject: a language feature (Transactions), a library (ballerina/http), a connector to an external system (ballerinax/salesforce), a webhook trigger (ballerinax/trigger.github), a tool (bal persist), a part of the platform (the runtime) or a cross-cutting topic (REST APIs).
  • Each node has a checklist (must_cover) of 5 to 20 concrete things a developer does with it. Every checklist item becomes one or more training samples.
  • Edges connect nodes: lib.http requires services and listeners, ballerinax/mysql implements ballerina/sql.

The rule that shapes everything: if a feature is missing from the graph, the model never sees training data for it. So coverage and accuracy come first, and every item cites the page it came from.

BThe big picture

Knowledge flows left to right. Sources are read, turned into YAML node files, loaded and validated by the Python package, and then published in several forms. Editing a title in the local viewer writes back into the YAML files.

Everything starts and ends with the YAML files in nodes/. They are the single source of truth; every output can be regenerated from them.

CThe building block: a node

A node is one YAML file named after its id. Here is a real one, lib.uuid, shortened to two of its eight items.

schema_version: "0.2"
id: lib.uuid
type: library
title: ballerina/uuid
summary: "Generates RFC 4122 UUIDs ..."
priority: important
status: draft
modules: [ballerina/uuid]
sources:
  - {url: "https://ballerina.io/learn/by-example/uuid-generation/", kind: bbe}
must_cover:
  - id: random_uuid
    text: "Generate a random (version 4) UUID string with
      `uuid:createType4AsString()` ..."
    difficulty: [beginner]
  - id: time_based_uuid
    text: "Generate a version 1 UUID ... with
      `uuid:createType1AsString()` ..."
  # ... 6 more items
edges:
  - {to: concept.strings, rel: uses, via: [random_uuid, validate_uuid]}
  - {to: concept.errors, rel: uses, via: [name_based_uuid, uuid_version, uuid_conversions]}
id
Unique name, prefixed by type: concept., lib., connector., trigger., tool., platform., topic.. The file must be called <id>.yaml.
title
What people see in the viewer: the real name, such as ballerina/uuid or Transactions.
priority
core, important or long_tail: how much training weight the subject deserves.
modules
Required for package nodes (library, connector, trigger): the Ballerina Central packages the node covers. Every package on Central is listed in exactly one node.
sources
Where the content came from: spec, bbe, central, docs, github or other.
must_cover
The checklist. Each item starts with a verb, names real syntax, and has a difficulty level.
edges
Links to other nodes. via says which of this node's items the link is about.

Nodes can also carry out_of_scope (things deliberately left to another node), notes (for reviewers, never sent to the generator) and replaced_by (for retired nodes or items). The three deprecated packages, lib.regex, lib.xmldata and lib.yaml, have status: deprecated and point to their replacements.

EEdges: how nodes connect

A small, real slice of the graph. Every edge drawn here exists in the node files.

RelationMeaningRule
requiresLearn the target first. A hard prerequisite.Must never form a cycle.
usesBuilds on the target. The most common edge (1,487 of them).Should name the items involved with via.
implementsProvides a concrete version of the target (a database connector for ballerina/sql, an AI model provider or vector store for ballerina/ai).Same as uses.
part_ofA piece of a bigger node (each ballerina/lang.* module is part of langlib; the FHIR implementation guides are part of the FHIR connector).Directed: child to parent.
relatedClosely connected, no direction.Symmetric: write it on one of the two nodes only.
alternative_toCan be used instead (ballerina/cache and ballerinax/redis).
counterpart_ofThe other side of a pair (client objects and services with listeners).

via and target_items make an edge precise. Instead of "uuid uses strings" in general, the edge says which uuid items rely on strings. The viewer uses this when you click a checklist item: it shows only the links that concern that item.

FValidation: what keeps the graph correct

loader.py reads every file, checks it against the schema in models.py, then checks the graph as a whole. Errors stop the load. Warnings are reported but allowed.

Errors

  • YAML that does not parse, or a file that is not one node
  • Fields that break the schema (wrong type, bad id pattern, a library, connector or trigger with no modules, duplicate item ids)
  • File name not matching the id, or two nodes with the same id
  • An edge to a node that does not exist, or to itself
  • The same edge twice, or a symmetric edge written on both nodes
  • via or target_items naming an item that does not exist
  • A cycle of requires edges (A needs B needs A)

Warnings

  • A uses or implements edge with no via or target_items
  • An orphan node with no edges in or out
  • More than 20 items (consider splitting)
  • No sources on the node or its items

Today: 0 errors, 0 warnings.

What happens when you run a command

  1. __main__.py parses the commandFor example validate nodes/.
  2. load_graph() reads every *.yamlEach file is parsed with PyYAML and turned into a Node object. Pydantic rejects anything that breaks the schema.
  3. validate_graph() checks the whole graphEdges, item references, duplicates, symmetric edges, the requires cycle check (a depth-first search), orphans and size warnings.
  4. A Graph object comes backIt holds all nodes and offers iter_items(), edges(rel), neighbors(), resolve(ref) and to_json().
  5. The command uses itstats counts, export writes JSON, view embeds the JSON into the HTML template, serve renders the viewer on each request.

IThe viewer

viewer.html is one file with the whole graph embedded as JSON. It needs no server: open it from disk or from GitHub Pages. It draws the graph with Cytoscape.js.

How title editing reaches the file

  1. You click Edit title and saveThe page sends POST /api/nodes/lib.uuid/title with {"title": "..."}.
  2. server.py checks the requestOnly from your own machine (127.0.0.1), only JSON, one non-empty line, and only for a node file that exists.
  3. It rewrites only the title: lineThe rest of the file stays exactly as written. The result is validated against the schema before it is saved.
  4. The viewer updates in placeThe panel, the graph label and search all show the new title.

JHow the graph was built

Version 1: the language spec

The first version covered only the Ballerina Language Specification 2024R1: 69 concept nodes and 849 items, each citing a spec section. That is on branch feature/spec-2024r1-concept-graph.

Version 2: the whole ecosystem

Version 2 merged related concepts, moved the lang library into library nodes, and added libraries, tools and topics. The work was split across ten research agents running in parallel, coordinated by a shared plan.

  1. Write a registryA plan file fixed all 159 ids, types, titles and priorities up front, so agents could link to each other's nodes before those nodes existed. It also set the rules: 5 to 20 items, cite every source, no invented APIs.
  2. Run ten agents in parallelOne merged concepts (69 → 50), one rebuilt the lang library (14 nodes), five wrote libraries (network, databases, data and IO, security and utilities, messaging and AI), two wrote tools, one wrote topics.
  3. Check every fileA per-file checker compared each node with the registry: id, type, title, item count, valid spec anchors, edge rules.
  4. Repoint old linksThe merge and langlib agents produced maps from every old item to its new home. A script used them to rewrite edges in all files that pointed at removed nodes.
  5. Validate and publishThe whole graph validated with no errors or warnings, then view and export rebuilt build/.

Version 3: every package, example and page

Version 3 set out to leave nothing out. It is on branch ballerina-graph.v3/complete.

  1. Download the whole catalogueThe Central API listed 856 ballerina/* and ballerinax/* packages. Each one was saved with its README and assigned to exactly one node.
  2. Add three node typesSchema 0.2 added connector, trigger and platform. The 14 ballerinax library nodes from v2 became connectors.
  3. Merge before addingFour AI provider nodes became one model-provider connector, Pinecone moved into the vector-store connector, and protobuf, UDP and WebSubHub were folded into gRPC, TCP and WebSub.
  4. Run thirteen agent groupsSeven connector groups (AI, healthcare and B2B, SAP and HR, Microsoft, Google and AWS, CRM and commerce, productivity and devtools, communication and finance), plus triggers, new libraries, deprecated packages, tools, platform and topics. 83 nodes were added.
  5. Measure coverage, fill the gapsA coverage script checked three lists: every Central package is in some node's modules, and every Ballerina by Example program and Learn page is cited. All three reached 100%.

Where a README disagreed with the module's source code, the agents followed the released source code and noted the difference in the node's notes. This happened often with generated connectors, whose READMEs sometimes show wrong method names, paths or config fields.

KFrom graph to training data

The graph does not generate samples itself. A separate dataset generator (the "harness") loads it as a Python library and walks the checklist.

from ballerina_graph import load_graph

g = load_graph("nodes/")
for node, item in g.iter_items():
    ref = g.ref(node, item)        # "lib.uuid#random_uuid"
    # generate samples for item.text, tag each sample with covers=[ref]

for edge in g.edges(rel="uses"):
    edge.source_items, edge.target_items   # items on both ends of the link
  • Item → samples. Each item's text is concrete enough to write a code example for, such as "Generate a random UUID string with uuid:createType4AsString()".
  • References. Every sample records the items it covers (lib.uuid#random_uuid), so you can measure which items have samples and which do not.
  • Priority and difficulty. core nodes can get more samples than long_tail ones, and difficulty levels let the generator vary beginner and advanced examples.
  • Edges. A generator can combine the items on both ends of an edge into one sample that uses several features together, such as an HTTP service that reads from MySQL.
  • Sources. sources_for(node, item) returns the pages behind an item, so a generator or reviewer can check a sample against the real docs.

LGit, branches and hosting

The repository is sajith-jeewantha/ballerina-ecosystem. Work happens on branches and reaches main through pull requests. GitHub Pages publishes main, so the hosted viewer always shows what is on main.

Simplified: dots stand for groups of commits, not single commits.

  • Live viewer: sajith-jeewantha.github.io/ballerina-ecosystem/ballerina-graph/build/viewer.html
  • Versions: mark finished versions with tags on main (v1.0.0, v2.0.0, v3.0.0) rather than long-lived version branches. A tag never moves; a branch does.
  • Other branches do not update themselves. After a merge, run git pull on main, and start new work from a fresh main.

MDaily workflow: changing the graph

  1. Start a branch from maingit checkout main && git pull && git checkout -b feature/<topic>
  2. Edit or add node filesCopy a similar node as a template. Use the real names, cite sources, keep 5 to 20 items, and link with edges.
  3. Validatepython -m ballerina_graph validate nodes/ until it prints OK with 0 warnings.
  4. Rebuild the outputsview and export, so build/ matches the nodes.
  5. Commit, push, open a pull requestMerge into main; GitHub Pages republishes the viewer. Tag it if it is a release.

NLimits and what could come next

  • Everything is a draft. 239 of the 242 nodes are status: draft (the other three are deprecated packages). Domain experts should review them, starting with the fast-moving AI, workflow and messaging libraries.
  • Depth varies. Every Central package is named in at least one item, but the hundreds of small generated connectors share grouped items, so they get fewer samples than popular packages such as Salesforce or GitHub.
  • Left out on purpose: features the agents could not confirm in the docs or source, such as S3 ACL methods or Bedrock guardrails. Each node's notes list what was skipped.
  • New packages appear. Central grows every week. Re-run the catalogue download and the coverage script to find packages that are not yet in any node.
  • Versions move. Library items follow the releases that were current when they were written. Re-check them when a new Ballerina release ships.
